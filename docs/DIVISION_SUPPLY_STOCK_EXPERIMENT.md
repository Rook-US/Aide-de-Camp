# Test 9: 1st Infantry Division at half stock

Prepared locally on 8 October 2026 for the installed game and save version 1.142. This is a disposable game-load experiment, not a production ADC supply control. The source is the player's game-written G-campaign save `Save7_10_2026_22_35_17`. The input copy is `Campaigns/001/G/ADC-TEST-9-DIVISION-50PCT-STOCK`, labeled **ADC Test 9 - 1st Division 50 Percent Stock**. The source is unchanged.

The four `supplyinstock` slots in `paths.dat` are **absolute quantities**, not stored percentages. The installed `Regiment.GetAvgSupplyState` divides a unit's applicable ammunition and provision/forage amounts by its active `strength`. The game saves `regiments.dat` total men as `strength + sick` and a sick percentage of that total. The builder reconstructs the integer active strength from those two saved fields, verifies that the sick percentage round-trips within `0.0001`, then sets **each of the four stock amounts to active strength / 2**. This targets 50% in the unit's own stock calculation. It is different from halving each existing stock amount, which would leave previously depleted units below 50%.

[`Build-DivisionHalfStockExperiment.ps1`](../scripts/Build-DivisionHalfStockExperiment.ps1) identifies the Union `1st Infantry Division` by saved faction, commander, name, and native tier. It follows saved parent IDs to five descendant groups and 18 combat units (11 infantry, two cavalry, and five artillery). Each combat unit is matched to one complete `paths.dat` record by the game's four-part identity: name, abbreviation, type, and commander. The script rejects ambiguous or missing matches, unexpected types or hierarchy counts, unsupported versions, malformed fixed-record counts, absent stock fields, and unreconstructable strength. It changes exactly 72 stock fields across those 18 units and the scenario label. No HQ path stock, unit parent, unit strength, group store, or incoming-flow value is edited. It verifies a full reparse and file hashes after copying; only `paths.dat` and `scenario.dat` differ from the source.

ADC loaded the prepared copy: all 18 existing creation-resave checks and nine town checks passed. This establishes structural compatibility with ADC, **not** game acceptance or the displayed result.

ADC's `PathRecordParser` now exposes the four finite stock amounts and their position within each fully parsed record, read-only. The baseline verification suite passed 178 checks, including a malformed-stock rejection. The prepared input passed 19 game-resave checks after this parser change. A [three-save comparison](../scripts/Check-DivisionSupplyResaves.ps1) is ready to resolve the 18 target units separately in the input, paused game save, and time-advanced game save by current-save hierarchy and the game's path identities; it reports category means and the HQ store icons. It refuses to treat one folder as multiple saves.

## In-game observation requested and completed

The player loaded **ADC Test 9 - 1st Division 50 Percent Stock**, made a paused game save, advanced time for several seconds without issuing orders, and made a second game save. The two game-written saves were compared to the input using full path identities and saved parent chains. The division's icons did not all read exactly 50% because the game's group aggregation differs from a unit's own stock percentage.

## Game-written results

The player supplied two version-1.142 saves. The folder names' times are **not** the experiment order: `Save8_10_2026_19_59_24` is labeled **ADC Test 9 - Paused**, and `Save8_10_2026_19_57_41` is labeled **ADC Test 9 - Unpaused**. The [identity-based comparison](../scripts/Check-DivisionSupplyResaves.ps1) found the same 18 target combat units beneath the division in all three saves. The paused game save retained **all 72 edited stock amounts exactly**. After time advanced, all 18 units changed at least one stock amount; changed-slot counts for small-arms ammunition, artillery ammunition, provisions, and forage were `(13,5,18,7)` respectively. The different counts include inactive ammunition slots, so they should not be read as per-branch consumption counts.

| Game-written state | Division small-arms | Division artillery | Division provisions | Division forage | I. CORPS four stores |
| --- | ---: | ---: | ---: | ---: | --- |
| Paused | 49.84532% | 50% | 49.88828% | 49.96748% | 90.49013%, 59.81517%, 89.04308%, 82.17515% |
| Time advanced | 56.96682% | 56.24148% | 73.27759% | 70.75156% | 92.66068%, 64.88287%, 96.36563%, 91.21972% |

The source input still had the old division group stores `(100,92.07277,100,100)`; the **paused game load recalculated** the division's displayed category stores from the edited subordinate amounts. Its values being close to, but not universally equal to, 50% confirms the distinction between per-unit active-strength percentages and HQ category aggregation. The parent corps changed less because it includes many other units. The time-advanced save demonstrates replenishment under the scenario's current conditions, not a universal refill rate. Both game saves passed all 19 ADC game-resave checks, and the full path comparison matched all 814 records by game identity (52 flow values and 472 stock arrays changed between the two game saves).

The comparison also checks the simple mean of relevant units' stock divided by `Total_Men + Wounded`. That mean matches the division's **artillery** and **forage** figures to saved precision in both game saves, but it does **not** match its small-arms or provisions figures. The latter category branches evidently apply additional eligibility or weighting; their exact formula remains unmapped. ADC therefore labels its input as a **unit stock percentage**, not a promise that the division's icon will equal the entered percentage.

This validates editing the four existing-unit stock amounts in `paths.dat` for the tested 1.142 combat hierarchy and observing their category effects in game. It does not validate writing a new `paths.dat` record for a newly created unit, overfilling beyond the game's observed stock target, or editing the independent incoming-flow value.
