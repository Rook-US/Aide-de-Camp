# Companion records for land units (7 October 2026)

Scope: the locally installed game's `Assembly-CSharp.dll`, its `ImportExportUnitData.CreateUnitFiles`, `SaveAdditionalUnitData`, `LoadAdditionalUnitData`, `CreateBattleDataFile`, and `ArmyGroup.SaveArmyGroupRef`/`GetArmyGroupRef` methods; ten local running saves whose `version.dat` is `1.142`, plus the controlled game resave in [`CREATION_EXPERIMENT.md`](CREATION_EXPERIMENT.md). The resave establishes a narrow accepted insertion route for the tested units and command; the general format investigation remains read-only for other combinations.

## Identity and relationships

* `groups.dat` and `regiments.dat` begin with counts and contain fixed 32- and 39-line records. The game writes each record's numeric ID as its **index in the corresponding live group or combat-unit list**. These are saved IDs, not absolute text line numbers. `regiments.dat` Parent_ID refers to the saved group ID. If a list is rebuilt or reordered, its IDs and all referencing files must be resolved again from that save.
* `garrisonrefs.dat` links a building to a live command with object name, abbreviation, runtime unit type, and commander ID. Its building key is name plus world x/y/z. For the sampled existing forts, the saved name plus commander resolves to one group; ADC's read-only resolver additionally requires root parent and saved tier 14. This is an explicit saved reference, not classification by a word in the name. The abbreviation is not in `groups.dat`; no numeric fort ID is present.
* `paths.dat` has **no numeric group or regiment ID** in its record prefix. The game loads a record by exact object name, abbreviated name, runtime unit type, and commander ID via `GetCampaignRegimentFromList`. For a combat unit, the first four identity values can be compared with `regiments.dat` offsets 1, 2, 4, and 5. The link must be unique; a text line number is not an identity.
* `armygrouprefs.dat` stores list-ordinal IDs that match the game-written `groups.dat` and `regiments.dat` IDs. Those references are concrete within a save, but must be rebuilt if IDs change.

A direct comparison of two September saves demonstrates the distinction: Fort Charlotte's same unnamed unit, with the same parent command, commander, type, home state, and position, moved from combat-unit ID 493 to 494 when another regiment was inserted earlier in the list. The absolute `paths.dat` line where its composite key appeared also moved. Neither the numeric ID alone across saves nor that line location proves creation or persistent identity.

## `armygrouprefs.dat` — fully bounded layout in sampled 1.142 saves

Let `G` be the count from `groups.dat` and `U` the count from `regiments.dat`. All offsets here are zero-based **within this file** and are used only to decode its sections, never to identify a command or unit across saves.

| Position | Game writer meaning |
| --- | --- |
| `0` | Group count `G`, if the game's army-group list exists; otherwise `0`. |
| `1 + i`, `0 ≤ i < G` | For a root group whose parent-list index is `-1`, `Regiment.GetArmyGroupCommanderID()`; for a non-root group, `-1`. These sampled saves have `-1` throughout. |
| `1 + G` | Second group count `G`. |
| `2 + G + 2i` | Saved group ID `i`. |
| `3 + G + 2i` | Group `Regiment.dlcw_isundercommandercampaign` Boolean. This is **not** a faction or side flag. |
| `2 + 3G` | Combat-unit count `U`. |
| `3 + 3G + 2j` | Saved combat-unit ID `j`. |
| `4 + 3G + 2j` | Combat-unit `Regiment.dlcw_isundercommandercampaign` Boolean. |

Expected line count is `3 + 3G + 2U` when the army-group list exists. All ten sampled saves have this exact length and counts, all 5,032 combat-unit IDs are their ordinal IDs, and every first-section entry is `-1`. Existing direct fort units have both `True` and `False` commander-campaign flags; there is no evidenced universal value for a newly created garrison unit. `CreateUnitFiles` writes this file when it writes `groups.dat` and `regiments.dat`. The optional `armygroups.dat` file was absent in the inspected latest save, despite `armygrouprefs.dat` being present.

## `paths.dat` — variable-length runtime state

The game writer starts with a count of all live `Regiment` components under `Units`, then serializes each component in Unity child order. In all ten sampled saves the count equals `G + U`; this is observed correspondence, not an ID mapping. The loader consumes the records sequentially and resolves each by the four-value identity above. The following sequence comes directly from the writer and loader; brackets denote count-delimited variable sections.

The read-only [`Inspect-PathRecords.ps1`](../scripts/Inspect-PathRecords.ps1) walks every count-delimited section and rejects a wrong end position. It parsed all ten local 1.142 files completely: 7,830 path records in total, including 216 records where cover-history or movement-path entries shift transfer time away from the fixed `start + 14` position. It also rejected a truncated copy and a copy marked version 1.143. No sampled record had a nonempty order queue, so the nested queue layout below is traced from game code but not exercised by these saves.

| Sequence | Saved value / interpretation |
| --- | --- |
| Identity | Object name; formatted abbreviation removed; runtime unit type; commander ID. |
| Cover and road history | Count of `lastcoverandroadai` integers, then each integer. |
| Rotation | First `lastwaypointrotation` element if present; otherwise the live transform's Euler Y rotation. |
| Movement paths | Count of nonempty `regimentpath` segments from the current path index. For each: last NavMesh corner x/y/z, then `pathstatus` for that segment (writer falls back to `2` if absent). This is waypoint state, not a general unit placement coordinate. |
| Battle and transfer state | `timedmovement`, `totaltimeoforderdelay`, `timeofarrival`; `isbattlestartunit`, `isbattlecallingunit`, `participatinginbattle`, `inbattle`; `transfertime`; `currenttransferposition` x/y/z; `startpointforpatrols` x/y/z. |
| Garrison and campaign state | `isgarrisonbasicunit`, `blockadeefficencyvalue`, `campaignstance`, `campaignstanceordered`, `cavalryorders`, `cavalryordersordered`, `fleetorders`, `timeofnotmoving`, `entrenchmentlevel`, `lastcampaignstatsupdate`, `morale`. `isgarrisonbasicunit` describes a basic unit, not every unit whose parent is a fort command. |
| Orders | Count plus values of `ordertypeactive` Booleans; `sourceunittoadvise` reference as object name/abbreviation/type/commander, or empty/empty/-1/-1; `orderstate`; count of `orderqueue` entries. Each order and courier has the nested layout below. |
| Supply and recruitment state | `latestupkeeppa`, `latestrecruitmentcostpa`, `onretreat`, `lastretreatiswithdrawal`; ammo-array count plus each ammo value; consumption-array count plus **three values per element** (`consumption`, `supplyfromdepots`, `supplylocal`). When consumption exists, the writer then emits `speedofsupply`, `latestreinforcements`, `reinforcementsneeded`, `supplystate`, and `unitrange.retreatangle` (or writer-constant `0` if `unitrange` is null). Next come the `supplyinstock` values **without their own count**; if the array is null the writer emits four zeros. Finally: `finishedrecruitment`, `battleflag`, `resetcampaignstance`, `missingavg`, a writer-constant `False` whose meaning is not established, `inbattleuntil`, and `priorwounded`. |
| Transport, theater and history | `usesea`, `useseaonly`, `userivers`, `userails`, `useroads`; `theaterposition` x/y/z; `reinforcementpriority`, `reformtime`, `reinforcementtype`, `servicehistory`, `prestige_casualties`, `lastcombatzonecount`. |
| Army-group and embarkation tail | `assignedarmygroup` reference as army-group object name plus commander ID, or empty plus `-1`; `assignedarmygroupcommander`; `embarkmentstarttime`, `embarkmentduration`, `embarkmentenemyfleetclose`, `lastembarkmentupdate`, `routrecovered2`, `dlcw_isundercommandercampaign`, `armygroupcoordinationremaining`. |

This table traces named runtime fields; it is **not yet a complete schema for writing a new record**. Valid initial values for order/courier links, path arrays, transport, supply, recruitment, and battle state have not been independently validated. The loader has version-dependent branches, so these observations must not be generalized beyond 1.142. `paths.dat` does not serialize a simple direct live transform x/y/z in the mapped prefix; `currenttransferposition`, patrol start, theater position, and NavMesh corners have separate meanings.

**ADC implementation:** `PathRecordParser` now consumes count-delimited sections and verifies full-file parseability for version `1.142`. `MatchPathRecords` links a unique existing regiment through the four saved identity values. The current-buffer offset is then used to patch both path names and the located transfer field. Unsupported versions and malformed path files disable those links; an unresolved link blocks renaming or ETA edits that would otherwise leave cross-file identities inconsistent. This supports safe edits of existing records. It does not supply initial values for a new path record.

Of 5,032 sampled combat-unit records, 4,595 have an exact four-value match in `paths.dat`. The other 437 have one path record with matching object name, runtime type, and commander, but a **different abbreviation**. There are no missing or ambiguous matches on the three-value subset. The game's `GetCampaignRegimentFromList` compares the abbreviation too, so ADC cannot declare those 437 path links confirmed merely because the other fields match. The differing abbreviation may reflect edits between saves; its in-game effect has not been observed. The latest sampled save has 520/520 exact four-value matches.

### Nested order queue, from the game writer

Each `orderqueue` entry writes, in order: advised-unit reference (object name, abbreviation, runtime type, commander, with empty/empty/-1/-1 for no unit); `startpathid`; `endpathid`; `processingtime`; `lastupdate`; `ordertype`; `timetomove`; `manualfinalrotation`; count of `receivedunits`, then four-value unit references; `initialunitwhogaveorder` four-value reference; count of `courierline` entries. Each courier line writes `type`, `processtime`, `courierref` four-value reference, `targetunit` four-value reference, `sourceunit` four-value reference, `lineactive`, and `lastupdate`. The loader reads these references using the same composite unit key. In the controlled 1.142 insertion test, the input omitted all new path records, and the game generated new 250-line records with zero order-queue entries on resave. This supports omitting a synthetic queue in that tested import route; it does not validate arbitrary queue contents.

## `battledata.dat` — campaign placement link

`CreateBattleDataFile` writes a 43-line header in the sampled save, including the deployment-record count at zero-based offset 42, then **15 lines per included command/unit**, followed by an economy-cycle count and two values per cycle. All ten sampled saves satisfy `line count = 43 + 15 × deployment count + 1 + 2 × cycle count`. The writer obtains map x from the live transform's x and map z from **negative** live transform z. Its inclusion filter considers campaign-map visibility; it does not serialize every combat unit separately. A further trace of `BattleUnits.import_battledata` maps the three values after entrenchment: the first becomes the z component of `Grp.objectiveposition` (with deployment x as its x component), the second becomes `Grp.orderactivationtime`, and the third becomes `Grp.trigger`. The inspected writer emits zero for all three in this campaign save route. Their saved purpose is therefore known; their nonzero behavior is untested.

| Deployment offset | Game-side interpretation |
| ---: | --- |
| 0 | Command or combat record ID in the corresponding current-save list. |
| 1 | Group formation. |
| 2–3 | Deployment map x and z; map z is negative world z. |
| 4–5 | Initial facing and entry angles. |
| 6 | Reinforcement delay. |
| 7–8 | AI group and AI stance. |
| 9 | Entrenchment percentage. |
| 10 | Objective-position z; loader pairs it with deployment x. |
| 11 | Order activation time. |
| 12 | Trigger. |
| 13 | `isGroup` Boolean selecting the ID list. |
| 14 | Readiness percentage. |

Across the ten sampled 1.142 saves, all **650 linked fort commands** have a group deployment record whose x equals the fort reference x and whose map z equals negative fort-reference world z, within `0.01`. Of **660 combat units directly parented to those linked fort commands**, none has its own `battledata.dat` deployment record. In the latest save, Fort Monroe's group ID 27 is deployed at `(1709.999, 860.0001)` while its fort reference is `(1709.999, 489.074, -860.0001)`; regiments 53 and 54 have Parent_ID 27 and no individual deployment record. The controlled Fort Monroe addition likewise loaded and appeared at the fort without its own deployment record, as confirmed by the player. This establishes that outcome for the tested 1.142 parent and record values, not an arbitrary new-unit placement rule.

The controlled [Test 3 town-placement experiment](TOWN_PLACEMENT_EXPERIMENT.md) adds a game acceptance check for an **existing root command**. The game loaded Union `I. CORPS` at New York after only its unique `battledata.dat` group deployment x/z changed to `(1777, 475)` and retained that position on manual resave. Its four directly subordinate divisions kept their original separate deployments. This resolves a single-HQ placement mapping and disproves any assumption that moving a parent implicitly relocates its descendants. A new root-command record at a selected town remains a separate creation gate.

## Game-side garrison routines

`BattleUnits.CreateGarrisonDummy` is a separate runtime operation for establishing a fort's garrison. It calls `CreateUnitDefault` for a tier-14 top command at the building's live transform position; if no existing unit is supplied, it calls `CreateUnitDefault` for a type-2 basic unit beneath it, passing `BattlefieldSetup.GetStateOfField(building position)` and `GamePrefs.basicgarrisonsize[building level]`, then sets `isgarrisonbasicunit = true`. `GetStateOfField` reads `terrainoccupation[x,-z]` and can fall back to the nearest **nation**; despite its name, that does not prove a playable home-state ID. The routine sets reciprocal `CBuilding.garrisonunit` and `Regiment.garrisonreference` object references. These facts explain the existing fort/command link and a basic unit's special flag, but do not provide a save-file constructor for an arbitrary combat unit under an already existing garrison.

`BattleUnits.DeployGarrison` is a **move existing unit** operation, not creation. It checks game settings, current deployment/transfer state, fort capacity, and attached-unit count, then calls `MoveUnit` into an existing fort's garrison command or creates a fort and dummy garrison if needed. ADC must not use this route as evidence that any new `regiments.dat` record can be initialized from a copied neighbor. `CreateUnitDefault` takes explicit parent unit, state, unit type, alliance, forced world position, size override, garrison flag, native tier override, and other inputs; its saved effects depend on runtime state and game configuration.

`CreateUnitDefault` calls `create_regiment` with 38 named inputs. Its IL shows the strength argument comes from `GetMaxUnitSize(alliance, unit type, 2, horse artillery)` unless a nonnegative `sizeoverride` is passed. It passes zero wounded, experience, drill, captured, sickness, transfer time, last transfer update, intelligence, and battles; `-1` for three unique-asset IDs; and the supplied native tier, recruiting type, uniform set, world position, and `isgarrison` flag. It then assigns the new object to its parent Unity transform. These are **runtime call arguments**, not a verified recipe for a `regiments.dat` plus `paths.dat` insert: other arguments are computed from campaign state, the method performs additional side effects, and the game writer later serializes the live object. The 38 parameter names were read from the installed `Assembly-CSharp.dll`; no unknown field has been assigned an inferred saved constant.

## Town and home-state identity

`SaveIIPAndTownData` writes each live town's `CityName`, transform x/y/z, capital flag, owner, and economic state. The `Town` runtime component has a `state` integer, but the inspected save writer does **not** serialize that field. `BattleUnits.ImportTowns` acquires town components from the Unity scene path `Battlemap/3DMap/Cities`. ADC's read-only `TownLocationParser` now consumes the counted IIP arrays, historical trades, town records, and economy tail before returning any town. It parsed all **103** named towns with finite game-written world positions in the player's 1.142 game resave; a truncated file and an impossible IIP count were rejected. The exact saved town name plus x/y/z is a concrete location identity within that save. No record ordinal or text line is used as an identity. This supports a searchable town list without state filtering, but **does not** prove that a new command placed at a selected town will load there.

`IIPsTowns.dat` alone cannot prove a town's playable home-state ID. Campaign `cities.dat` in the sampled `Campaigns/001/G` folder has only three city override records and is not a full town/state registry. `GetStateOfField` reads a terrain-occupation map and may return a nearest-nation fallback, so using its name alone as proof of a home-state mapping would be wrong. The dated texture mapping below provides the missing state link for this installed build's 1861 interval.

### Dated 1861 town-to-state mapping (installed build and the player's 1.142 save)

### Supply and perk fields: interpretation traced, creation still gated

The game's `SaveAdditionalUnitData` writes the runtime supply arrays in `paths.dat`: a counted ammunition array; a counted consumption array with `consumption`, `supplyfromdepots`, and `supplylocal` for each element; then, when that count is nonzero, `speedofsupply`, `latestreinforcements`, `reinforcementsneeded`, `supplystate`, retreat angle, and four `supplyinstock` values. `Regiment.GetAvgSupplyState` confirms that stock is **absolute supply amount**, not a percentage: it divides stock by at least one soldier. For type 2 it starts from stock index 1; for other types, index 0. For unit types 1, 2, or 4 it averages that ratio with `(stock[2] + stock[3]) / strength` over three terms; otherwise it averages the first ratio with `stock[2] / strength` over two terms. `BattleUnits.CalculateOriginalSupplyStates` starts from side ammunition and supply-level settings, calculates supply lines and group reserves; `UpdateCampaignSupplyStates` recomputes group supply from live strength and stock. Thus setting a single `supplystate` value in a new path record would not constitute an independently valid editable supply level. The game generated complete new path records after the tested no-path insertion, but there is no controlled chosen-supply change and in-game verification yet. **Unable to proceed** with editable starting supply; evidence needed is a controlled supply choice with a game-written before/after path record and visible in-game supply for that unit.

**Observed stock after game-generated import, 8 October 2026.** The read-only [supply audit](../scripts/Audit-NewUnitSupply.ps1) resolves the six new units through the game's four-value path identity and exposes counted ammunition, consumption, the five-value supply header, and four stock values after a full parse. In the player's 7 October 1.142 game resave, each of the six newly imported combat units has ammunition `(1,1,1)`, four zero consumption triples, and supply header `(1,0,0,1,0)`. The infantry's stock is `(999.1487,1000,1000,1000)` with `regiments.dat` total men 1000; cavalry is `(599.4893,600,600,600)` with 600 men; the four artillery units have total men 60 and stock `(60,59.92737,60,60)` at Fort Monroe or `(60,59.94893,60,60)` for the three division battalions. These are game-written values **after** a campaign save, including small differences in one component. They show that the game populated stocks and that a single stock amount cannot be copied as a universal constant. They do not establish an editable starting-supply choice or an exact initialization formula.

The installed `Regiment.FillUpStock(float)` method provides another supply-field interpretation. It checks for a nonempty stock array, calculates live strength and maximum unit size, then fills stock index 2 and branch-dependent indexes 0, 1, and 3 toward a requested strength-scaled amount. It caps each fill at the remaining gap to strength and returns the average amount filled across affected categories. This confirms that stock indexes are separate consumable categories and can change together through game logic. The method does not establish how a user-selected initial supply setting would initialize all four stock values, or the coupled ammunition and consumption fields.

[Test 6](SUPPLY_STOCK_EXPERIMENT.md) is a disposable existing-infantry stock experiment: indexes 0 and 2 were changed from their game-written amounts to 500 out of 1000, while all other supply fields remained unchanged. The player's paused game resave retained the exact stock, and the time-advanced save replenished those indexes to `556.0485` and `677.2684`. The connected division's group-store values also changed. The player correctly noted that a combat unit's campaign-map supply percentage is not directly inspectable like an independent HQ's; the installed manual confirms that the HQ panel's main supply percentage is incoming flow, while carried stores have separate icons. This validates existing-unit stock input in version 1.142, not a new-unit supply choice or a general displayed percentage.

The [campaign supply hierarchy map](SUPPLY_HIERARCHY_MAP.md) separates the HQ's visible flow (`CampaignArmyPanel.UpdateStats` reads `supplystate`) from its carried-store icons (`CampaignArmyPanel.SetIcons` reads `groupsupplystate`). The installed `Regiment.UpdateGroupStrength` aggregates attached combat-unit stocks into group ratios, and `BattleUnits.UpdateCampaignSupplyStates` also uses a top supply unit's own stock and group strength. [Test 8](HQ_SUPPLY_FLOW_EXPERIMENT.md) proved that an edited HQ flow value survives a paused resave but returns to 100% as soon as campaign time advances; that raw field is transient, not an editable starting supply setting. [Test 9](DIVISION_SUPPLY_STOCK_EXPERIMENT.md) validates four-category edits to 18 existing combat units and supports ADC's [existing-unit stock editor](SUPPLY_STOCK_EDITOR.md), but chosen stock initialization for a new unit and the precise distribution rules remain unverified.

Perk records are three values per slot: perk ID, level, and experience. The installed `Config/PerkTooltipsArmyCampaign.txt` declares 18 command perk IDs; `Config/PerkBattleTooltips.txt` declares 19 combat perk IDs. These files provide names and described effects, while the game code gives saved interpretation: `Regiment.ChoosePerk` requires an unused slot whose experience has reached 1, rejects duplicate IDs, then writes the selected ID, resets experience to 0, and sets level 0. `Regiment.HasPerk` and `GetPerkLevel` read those IDs and levels; `IncreasePerkExp` advances them. The player's game-written resave contains assigned IDs 3, 5, 7, 8, 12, and 16 on commands and IDs 1, 2, 3, 4, 5, 7, 9, 14, and 15 on combat units, proving those values occur in real records. [Test 4](PERK_ASSIGNMENT_EXPERIMENT.md) confirms that a 1.142 infantry unit with an empty slot at experience 1 receives a perk choice in game, and choosing Zouave I causes the game to save `2,0,0`. [Test 5](DIRECT_PERK_EXPERIMENT.md) directly inserted that same `2,0,0` triple in the first slot of the same infantry unit; the player confirmed success in game and the game retained it on resave. This is a **narrow validated write combination**, not a rule for other perks, unit branches, command perks, or starting slot availability in a newly created unit. **Unable to proceed** with a general editable starting-perk write control until those rules are tested. The creation UI must not populate unverified perk triples from a neighbor record.

**Perk levels and progress in the installed build.** `GameVars` initializes `maxperklevels` to **3**; `Regiment.GetPerkLevel` caps the returned level at `maxperklevels - 1 = 2`. Both installed tooltip entries explicitly include Cold steel **I/II/III** (`9/0`, `9/1`, `9/2`) and Zouave **I/II/III** (`2/0`, `2/1`, `2/2`). `Regiment.IncreasePerkExp` adds the awarded amount to an assigned perk's saved fractional experience. When it exceeds 1 and the saved level is below 2, the method adds one level and subtracts 1 experience; at level 2 it caps any excess at 1. Thus level **1 / II is not the maximum**, and a saved level-1 experience of zero means no accumulated progress since that level was set, not that the level is capped. The exact game-code comparison is `> 1`, not `>= 1`.

The read-only [`Audit-PerkProgress.py`](../scripts/Audit-PerkProgress.py) checked all direct G save folders. In the latest game resave, all four **Zouave II** records have experience `0`; two **Zouave III** records are at level `2`, experience `1`. Sixteen of seventeen **Cold Steel II** records have experience `0`; `2nd US Cavalry` has `0.5080001`. That same named/type/commander/home-state record changed from `9,1,0` in the 4 October 10:36 save to `9,1,0.5080001` in the 4 October 19:33 save and retained it in the latest save. This is observed progress at level II, independent of a guessed unit-ID or text-line link. Comparing units corroborates the code's range but is not needed to discover it.

The award code explains some zero-progress cases without proving any particular battle history. In tactical `Regiment.SufferCasualties`, melee casualties credited to the opposing unit can call `IncreasePerkExp(..., 9)` for Cold Steel when the casualty-taking unit has runtime type 1 or 4; the campaign-mode branch skips this call. For Zouave, `IncreaseCasualtyPerks` calls `IncreasePerkExp(..., 2)` for an infantry-type attacker (`unittyp` 0 or 3) only while its `liedown` flag is true and it inflicts casualties. The installed tooltips summarize these as leveling through melees and fighting prone. Autoresolve also has a separate general perk-experience call, so the saved progress alone cannot establish exactly which event awarded `2nd US Cavalry` its `0.5080001`. An in-game battle/after-save comparison is still needed before diagnosing a specific stalled unit as a bug.
